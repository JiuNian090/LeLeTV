# 版本更新 — 版本号 & 版本日志

统一负责版本发布：更新 `CHANGELOG.md`、升级 `VERSION.txt`，并同步 `README.md`（版本号、更新日志摘要，以及本次改动涉及的正文内容）。
构建由 Cloudflare 在部署时自动完成，本地无需构建。

> ⚠️ **强制规则：** 任何「更新更新日志 / 更新版本 / 发布新版本 / 打 tag / release」请求都必须通过本技能执行，禁止凭记忆手改版本号与版本日志。

## 工作流程

### 1. 更新代码图谱索引

发版前先刷新 CodeGraph 索引，保证后续影响分析与调用链查询基于最新代码（命令细则见 `.agents/rules/code-graph-rules.md`）：

```bash
codegraph sync
```

- `sync` 是增量刷新，日常发版用它即可
- 仅当索引结构异常时才用 `codegraph index --force` 全量重建；若报 `EPERM ... database file is in use`，说明 CodeGraph 服务正占用索引库，先停掉该服务再重试
- 该命令在受限沙箱下可能因写入工作区外的遥测文件而返回非 0 退出码；功能本身已完成，看输出中的同步结果即可

### 2. 确认版本号

询问或确认用户提供的新版本号（如 `v3.5.2`）。

### 3. 读取当前版本

读取 `VERSION.txt` 了解当前版本。

### 4. 获取 git 提交记录（含日期）

```bash
git log --format="%ad %h %s" --date=short -30
```

了解自上个版本以来的所有提交及其提交日期，用于编写更新日志与确定版本日期。

需要查看提交详情时：

```bash
git log --format="=== %h %ad %s%n%b" --date=short <上个发布提交>..HEAD
```

### 5. 更新 CHANGELOG.md

在 `CHANGELOG.md` 顶部插入新条目。

**分类与 emoji（保持项目已有风格）：**

| 分类 | emoji | 适用场景 |
|------|-------|---------|
| 新功能 | 🎉 新增 | 用户能直接使用的新能力（feat） |
| 体验优化 | ✨ 优化 | 交互、速度、易用性提升（improve / optimize / perf） |
| 问题修复 | 🔧 修复 | 用户遇到的功能异常修复（fix / patch） |
| 界面样式 | 🎨 样式 | 视觉、排版、动效调整（style / ui / theme） |
| 性能/配置 | ⚡ 调整 | 后台优化、配置项变化（config / setting） |

> 纯内部改动（重构 refactor、模块拆分、文档 docs、版本管理、构建配置、静态资源 hash 等）不记入更新日志，除非影响了用户可感知的性能或稳定性。

**面向普通用户的编写原则（严格执行）：**

每条日志只描述**用户能感知到的变化**，严禁出现以下内容：

- ❌ **专业术语**：函数名、变量名、类名、CSS 选择器、正则表达式等代码级细节
  - 如 `resetSearchArea 函数` → ❌ → 应写为「关闭搜索结果后恢复搜索区域」
- ❌ **内部数据**：API 源名称列表、数量统计、时间数值、TTL 值、数据库字段
  - 如「缓存 TTL 调整为 1800 秒」→ ❌ → 应直接写「优化缓存策略」
- ❌ **管理类功能**：环境变量配置、CI/CD 调整、Git 配置、部署设置、脚本更新
  - 如在 401 问题排查中发现的 HIDDENKEY 环境变量 → **不记入更新日志**
- ❌ **代码清理**：重构、重命名、拆分模块、清理废弃代码等纯内部改动
  - 除非影响了用户能感知的性能或稳定性，否则不记录
- ❌ **版本管理**：版本号更新、构建配置、静态资源 hash 更新等
  - 版本号本身就写在更新日志标题里，不需要再写一条「更新版本号」

**正确示例：**
```
✅ 修复 播放页详情折叠按钮点击无响应的问题
✅ 优化 详情区域无演员/简介数据时自动隐藏切换按钮
✅ 新增 移动端全屏搜索覆盖层，支持搜索历史和键盘交互
```

**格式：**

```markdown
### {新版本号} ({YYYY-MM-DD})
- {emoji} {面向用户的描述}
```

**日期规则（严格执行）：** `{YYYY-MM-DD}` 必须取**该版本 git 提交的实际日期**，严禁使用执行任务当天的日期（任务/系统日期）。

- 取值：该版本发布提交的日期 → `git log -1 --format="%ad" --date=short <发布提交>`
- 定位发布提交：`git log --format="%ad %h %s" --date=short | grep -i release`
- 一个版本对应多个提交时，取该版本的（最后）发布提交日期
- 即使系统提示的「今天」与提交日期不一致，也必须以提交日期为准

### 6. 更新 VERSION.txt

将新版本号写入 `VERSION.txt`（如 `v3.5.2`）。

### 7. 同步 README.md（必查：版本信息 + 正文内容）

发版不只是改更新日志。**本次版本改了什么，README 的正文就要跟着改到与代码一致。**
每次发版都要检查下面两类内容，缺一不可：

**① 版本相关信息（每次必改）**

1. **当前版本号** — 「🗂️ 缓存与版本管理 › 版本管理」章节中的 `VERSION.txt`（当前 `vX.Y.Z`），改为新版本号
2. **更新日志** — 「📝 更新日志」章节（默认保留最近 3 条），把新版本条目同步到顶部，并移除被挤出的过期条目

**② 与本次改动对应的正文内容（逐项核对，禁止跳过）**

对照第 4 步拿到的提交记录，判断本次版本涉及 README 的哪些章节，并逐项改到与代码一致：

| 本次改动涉及 | 需要核对的 README 章节 |
|-------------|----------------------|
| 新增/调整用户可感知的功能 | 「✨ 功能特性」下对应小节 |
| 新增或改动 API 路由、数据表、上下游依赖 | 「🏗️ 架构说明 › 生产部署架构」、对应系统的「相关文件」表 |
| 新增/删除/移动源文件或目录 | 「🏗️ 架构说明 › 目录结构」（含模块数量、子目录说明） |
| 部署步骤、迁移脚本、绑定、构建命令变化 | 「📦 部署指南」，如 D1 迁移脚本清单要补上新脚本 |
| 新增/变更环境变量 | 「⚙️ 环境变量」下的 Worker / Pages / 本地三张表 |
| 缓存策略、存储键、TTL 变化 | 「🗂️ 缓存与版本管理」下的响应头与应用层缓存表 |
| 引入或升级第三方依赖 | 「🧰 技术栈」 |

核对原则：

- README 中**已有对应描述**的，必须一并改成与代码一致（数量、清单、表格行、流程示意都算）
- README 中**尚无该章节**但本次改动值得记录的，补充相应内容
- 判据是「README 现有描述是否已与代码不符」，与更新日志的取舍标准不同——纯内部重构在更新日志里不写，但只要让 README 描述失真就必须改
- 若确实对应不上任何章节，在结果中显式说明「本次无需改动正文」及原因，不得默认跳过

### 8. 验证

检查以下内容是否已正确更新：

- `VERSION.txt` — 版本号已更新
- `CHANGELOG.md` — 已插入新版本条目（日期为该版本提交日期）
- `README.md` — ① 版本号与更新日志摘要已同步；② 本次改动涉及的正文章节已核对并更新（或已说明无需改动的原因）

### 9. 构建（如项目需要）

若本次改动涉及源码/样式，运行 `npm run build` 刷新版本注入与静态资源哈希：

```bash
npm run build
```
